## 排查「连接后台失败」（11:15，COM4 串口）
- **不是网络/后台问题，也不是 token 问题**。设备日志实测：
  `HTTP code: 200` / `Content-Length: 105984` / `[MEM] colorBuf alloc failed` / `colorBuf alloc failed, skip 2bpp`
  → 每次重试都走 `[BOOT] Content not ready, retry N/4`，屏幕恒显示 `Generating...`。
- 根因：768×552 四色屏 2bpp 全帧缓冲 `COLOR_BUF_LEN=(768*552)/4=105,984`，`ensureColorBuf()` 直接 `malloc`，
  而请求时刻 free heap 仅 137,588（WiFi+mbedTLS+LittleFS 已把堆打散），拿不到 106KB 连续块。
- 静态占用参考：`imgBuf[96*552=52,992]` + 其他 = 92,976（RAM 28.4%/327,680），开机堆约 234KB。
- 待定方案：①网络流式直接写屏（去掉 colorBuf，最优）②降 1bpp（丢四色）③开机预分配（TLS 只剩 ~30KB，风险高）。
- **本地成功 / 服务器失败的差异已定位**：`ensureColorBuf()` 的调用时机不同。
  BMP 分支（`network.cpp:758`）逐行读进静态 `imgBuf`，`http.end()` 之后才在 `epdDisplay` 里申请 106KB → 堆完整，能成功；
  2bpp 分支（`network.cpp:707`）在 HTTPS 连接**还开着**时申请 → TLS 收发缓冲把堆切碎 → 失败。
  `render.py:102-111` 设备未绑定 owner 时直接返回 BMP 配对图（不进 2bpp），`render.py:215` 才走 `image_to_raw_2bpp`。
- **流式写屏可行性已确认（不涉及局部刷新）**：墨水屏是「写面板 RAM → 0x12 整屏刷新」两步，
  驱动本来就在逐行写：`epd398WriteRows2bpp` 循环 552 次 `0x83 设窗 + 0x10 写 192B`，最后才 `epd398Refresh()`。
  MCU 侧 106KB 只是暂存区。`epd398WriteRowsMono` 已是流式范式（栈上 `row[192]`，注释写明「避免再申请一份 106KB 缓冲」）。
  `epdSupportsPartialRefresh()` 返回 false，本方案不需要局部刷新能力。
- 调用链备忘：`network.cpp` 填 `colorBuf` + `useColorBuf=true` → `display.cpp:723` → `epdDisplay2bpp` → `epd398WriteRows2bpp` → `epd398Refresh`。

## 改为流式写屏（11:30，已编译，待烧录）
- 新增 `epdStream2bppBegin/Row/Flush/Abort`（epd_driver.cpp，仅 NZ07 分支）；`network.cpp` 新增
  `stream2bppToPanel()`，每读 192 字节就 `0x83 设窗 + 0x10 写一行`，栈上行缓冲，不再 malloc 106KB。
- 保留原有去重语义：流式时边写边累加校验和 → `useStreamedPanel` + `streamedPanelChecksum`（均在 `EPD_BPP>=2` 下声明）。
  `main.cpp` 校验和分支优先用流式值；`display.cpp smartDisplay()` 若 `useStreamedPanel` 则只做 `epdStream2bppFlush()`（一次 0x12 整屏刷新）；
  内容未变化时走 `epdStream2bppAbort()` 只关电不刷新。
- 编译结果：RAM 92,984（+8B）/ 327,680，Flash 1,266,795；`epd_42_wsv2_ssd1683_c3_promini`（EPD_BPP=1）也编译通过，未受影响。
- **烧录踩坑**：`pio run -t upload` 报 `MissingPackageManifestError`（缺 tool-esptoolpy 包），改用
  `~/.platformio/packages/tool-esptool/esptool.exe --chip esp32c3 -p COM4 -b 460800 write-flash -z 0x10000 firmware.bin`
  **只烧 APP 分区**，避免 merged bin 从 0x0 覆盖 NVS（nvs 0x9000-0xE000 存 WiFi/server/token）。
- 烧录时 COM4 报 `ERROR_GEN_FAILURE`（设备在、驱动打不开），疑似前面反复 DTR/RTS 复位把 USB-CDC 弄挂或设备进休眠，需拔插 USB 恢复。
- 附带发现：`[BAT] raw=528 vbat=0.85V` 明显异常（USB 供电下不可能 0.85V），且 `v=0.85` 会带进 render URL；
  `setup()` 里 `analogSetAttenuation` 只在 WROOM02/SMT_WROOM32E/YD_S3 三个 profile 生效，`BOARD_PROFILE_ESP32_C3` 不在其中。
- 另注：从 PC 直接 curl `/api/render` 返回 401 `设备 Token 无效或缺失` 是**正常的**（没带 X-Device-Token）；
  设备 token 走 `POST /api/device/{mac}/token`，存服务端 device state 的 `auth_token` + 设备 NVS `device_token`。
  `.env` 里的 `ADMIN_TOKEN` 是管理端登录令牌，和它无关。
- PlatformIO 可用：`python -m platformio`（6.2.0），env `epd_398_nz07_a0_c3_promini`。COM4 复位时序：DTR=0/RTS=0 才会正常启动（`boot:0xd`）。
