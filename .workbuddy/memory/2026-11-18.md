## PlatformIO 下载卡住的排查结论（重要经验）
- 现象：`pio run` 长时间停在 `Downloading 0%`，`~/.platformio/.cache/downloads` 里 tmp 文件不增长。
- 根因：PlatformIO 的包地址 `dl.registry.platformio.org` 会 **302 跳转到 GitHub Releases**（`github.com/ivankravets/pioreg-ci-mirror`），
  而本机经 VPN 访问 GitHub 只有约 40 KB/s，等于卡死。工具链 `toolchain-riscv32-esp` 单包就有 933 MB（解压 2.4GB）。
- 可用绕过：在 `platformio.ini` 临时加 `platform_packages = platformio/toolchain-xxx @ https://gh-proxy.com/<github地址>`，
  并设置 `NO_PROXY=gh-proxy.com`（gh-proxy 直连可达 1.2~12 MB/s，走 VPN 反而慢）。
- 剩下的 `tool-xtensa-esp-elf-gdb` / `framework-arduinoespressif32` / `tool-esptool` 等仍需逐个找跳转地址，成本高，本次未继续。
- 已在本机装好 PlatformIO Core 6.2（`python -m platformio`），两个工具链已落盘在 `~/.platformio/packages/`。

## 预览面板：改按物理尺寸显示（3.98" 不再比 5.83" 大）
- **现象**：加 3.98" 后预览卡片比 5.83" 还宽。原因：`eink-preview-panel.tsx` 把卡片宽度写成
  `width: ${screenW}px`（像素 1:1），而 3.98"(768×552, 238DPI) 像素数 > 5.83"(648×480, 138DPI)，
  但物理尺寸小得多。
- **改法**：`screen-size-select.tsx` 的 `OPTIONS` → `SCREEN_OPTIONS`，每项加 `dispW`（推荐显示宽度），
  基准 = 4.2" 的 1:1（400px ÷ 3.36in ≈ 119 px/in）：
  4.2"→400 / 2.9"→317 / 3.98"→385 / 5.83"→558。导出 `getDisplayWidth(w,h)` 反查。
- **右栏窄时要等比缩放，不能靠 max-w-full 硬压**：都压成同一宽度就丢了物理比例。
  面板里用 `ResizeObserver` 量 Card 实际宽度，`factor = min(1, availW / 558)`，
  `displayW = round(rawW * factor)`。实测本机右栏只有 **360px** → factor 0.645。
- **踩坑（重要）**：把 `lg:grid-cols-[520px_1fr]` 改成 `[520px_minmax(0,1fr)]` 后，
  Tailwind 重新生成任意值类，规则顺序变化导致 `grid-cols-1` 反超 `lg:` 媒体查询 →
  **页面降级成单列，预览面板掉到模式列表下方**。修法：恢复原类名，改给右列 div 加 `min-w-0`。
  结论：改 Tailwind 任意值类名要当心，宁可加辅助类也不要动已有的 arbitrary value。
- 顺手去掉 `height: calc(55vh - 80px)`，改 `minHeight: displayH`（也符合不用 calc 的偏好）。

## 预览改「实物大小」+ 配置页加宽（第二轮）
- **目标**：预览不能比实物小。基准改用 CSS 标准 **1px = 1/96 英寸**（旧版用 4.2" 的 400px 当基准 ≈ 119px/in，偏大 24% 但被缩放系数吃掉）。
  新 dispW：2.9"→256 / 3.98"→310 / 4.2"→323 / 5.83"→450（`screen-size-select.tsx`，导出 `MAX_DISP_W`）。
- **不要用 JS 量宽度**：`ResizeObserver` + state 会拿到首帧未约束的值（实测 `card400` 但 `avail1400`），
  缩放系数算错。改成纯 CSS：`width: rawW; maxWidth: 100%; aspectRatio: w/h`，
  放得下就 1:1，放不下自动等比缩。实测 3.98" 框 = 310×223，图片 `fill` 正好铺满。
- **CardContent 的 `p-6` 会盖掉 `className="p-0"`**（Tailwind 同属性顺序问题），必须写
  `style={{ padding: 0 }}`。否则内容区少 48px，预览被压小、底部三个按钮换行。
- **布局**：`grid-cols-[520px_1fr]` → `flex`，左栏 `lg:w-[660px] lg:shrink min-w-0`，
  右栏 `lg:flex-1 lg:min-w-[320px]`（保证预览不被压没）。页面容器 `max-w-6xl` → `max-w-7xl`，
  `navbar.tsx` 两处 `max-w-6xl` 同步改 `max-w-7xl` 保持左右对齐。
- **模式卡仍是一行 4 个**（`grid-cols-3 sm:grid-cols-4`），靠加宽左栏而不是减列数解决文字换行；
  卡片描述 `text-[11px]` → `text-[13px]`。
- 踩坑备忘：**别再用 Tailwind 任意值改已有 grid 类名**（上次 `lg:grid-cols-[520px_minmax(0,1fr)]`
  导致 `grid-cols-1` 反超媒体查询、整页降级单列）。要改布局结构就直接换 flex。
- /zh/config 存在一条 RootLayout 的 hydration 警告（dev overlay 左下角红色 1 Issue），
  与本次改动无关，浏览器扩展/PageviewTracker 一类问题，production 不受影响。

## 相册「选图不进裁切窗」根因修复（17:35）
- 现象：config 页点相册「添加照片」选完图，裁切窗不出现，什么也不发生。
- 根因：`album-modal.tsx` 的 onChange 写成
  `const list = e.target.files; e.currentTarget.value = ""; pickFiles(list);`
  —— **`input.value = ""` 会连带清空 `input.files` 返回的那个 FileList 对象**（SameObject + 内容随 value 重置），
  所以 `list.length` 变成 0，`pickFiles` 第一行就 return。
- 实测证据：临时页 `/zh/album-test` 跑探针 → `FileList 探针：清空 value 前=1，清空后=0`。
- 修法：`const files = e.target.files ? Array.from(e.target.files) : []; e.target.value = ""; pickFiles(files);`
  并把 `pickFiles` 形参从 `FileList | null` 改成 `File[]`，空列表时给出文案（超 6 张 / 非图片）。
- 验证（dev 3100 + `DataTransfer` 注入真实 File 派发 change，模拟用户选图不可自动化）：
  裁切窗弹出（768×552）→「使用这张」导出 21KB → 自动进入队列第二张 → 再导出 16KB → 缩略图两张按 16:9 显示。
  然后删临时页、重新 build、重启 3000，线上点「相册→预览」弹窗正常。
- 经验：**清空 `<input type=file>.value` 前必须先 `Array.from(files)`**，否则拿到空列表。
  这类「点击无反应」优先怀疑 FileList 已被清空，而不是组件渲染问题。
- 遗留：`/preview`（无设备体验）页没有 MY_ALBUM 分支，在那里点相册只会渲染一张空图，没有裁切入口。

## 设备卡 "Generating..." 无限重启（17:45）
- 现象：墨水屏开机后一直显示 Generating...，重试 4 次后重启，循环。**与图片/模式渲染无关**。
- 定位（关键）：用户给了 COM4，直接抓串口（`python` 系统解释器自带 pyserial 3.5，backend venv 没有）：
  ```
  GET http://192.168.137.1:8080/api/render?...&w=768&h=552&bpp=2&colors=4
  HTTP code: 400
  Response: Invalid host header
  [BOOT] Content not ready, retry 2/4
  ```
- 根因：`api/index.py` 的 `TrustedHostMiddleware` 白名单只有 `*.inksight.site` / localhost / test，
  **不含局域网 IP**。设备走 Windows 热点网关 `192.168.137.1` 访问，Host 头不在白名单 → 中间件在路由前就 400，
  所以 `render_logs` 里一条记录都没有（这个"日志是空的"就是中间件拦截的特征）。该加固来自 4 月提交 91507e6。
- 修法：`api/index.py` 加 `LanTrustedHostMiddleware(TrustedHostMiddleware)`，Host 是私有/环回字面 IP 时直接放行
  （127/8、10/8、172.16/12、192.168/16、169.254/16），其余仍走原白名单。
- 验证：`http://192.168.137.1:8080/api/health` 200；伪造 `Host: evil.example.com` 仍 400；
  设备 17:45:04 有一条 `MY_ALBUM success 3.2s`，`last_refresh_at` 同步更新。
- 排查技巧：
  - **判断"后端没收到请求"还是"收到但失败"，先看 `render_logs` 有没有记录**：一条都没有通常是中间件/CORS 层拦截。
  - ESP32-C3 的 USB CDC 在 `ESP.restart()` 时会断开重连，串口读取抛 `ClearCommError` / `PermissionError`，
    需要循环重试打开端口（`firmware/capture_serial.py` 就是干这个的）。
- 附带发现（未处理）：串口里 `[BAT] raw=563.8 vbat=0.91V`，电压读数明显异常（满电应 ~4.2V），
  可能是未接电池或 ADC 分压配置问题，用户说"没问题"暂不动。
